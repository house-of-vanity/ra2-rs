# Сетевой каркас и проверка качества

В меню Multiplayer доступны соединения по IP и через iroh. Ниже отдельно описаны инструментальный стенд и игровой
адаптер. Сетевой стенд собирается без Robot Arena 2, окна, GPU, ALSA и Wayland.

## Команды

```bash
# Протокол, адаптеры, физические регрессии и 66 сетевых экспериментов.
cargo test --locked -p arena-net -p arena-net-io -p arena-net-lab

# Та же матрица качества с отчётами и трассами каждого эксперимента.
cargo run --locked -p arena-net-lab -- --out logs/net-report

# Быстро воспроизвести один случай.
cargo run --locked -p arena-net-lab -- --profile rtt-200-loss --players 4 --seed 41

# Отдельный интеграционный тест настоящих UDP-сокетов: требует разрешения ОС.
cargo test --locked -p arena-net-io --features real-sockets
```

На NixOS команды можно выполнять внутри `nix-shell`. Зависимости графики самой
игры в дерево зависимостей стенда не входят. Тесты используют только виртуальное
время; реальные сокеты по умолчанию не нужны. В ограниченной среде агента создание
UDP-сокета запрещено (`EPERM`), поэтому этот тест выделен отдельной feature,
а протокол обнаружения LAN также проверяется обычными тестами без сокетов.

## Границы модулей

- `arena-net`: стабильные ID, версия протокола, ограниченный бинарный кодек,
  лобби/совместимость/BOT, буфер ввода, снимки, replay/reconciliation,
  интерполяция, часы и контракт `DatagramIo`. Здесь нет ECS и адресов сокетов.
- `arena-net-io`: пакетный слой Lightyear 0.31 с независимыми каналами ввода,
  снимков, надёжных событий и надёжной загрузки BOT; ниже — сменяемый IO.
  Игровые датаграммы передаются по UDP или iroh. Для поиска хоста используются IPv4 broadcast в LAN и Mainline DHT по коду комнаты.
- `arena-net-lab`: стенд Rapier 0.36.1, сценарий, имитация сети и отчётность.
  Для него нужны только минимальные Bevy App/ECS/Time, используемые Lightyear;
  рендеринг не подключается.

Используется пакетный слой Lightyear, а не его автоматическая ECS-репликация
или готовый Avian-adapter. Состояние Rapier и наших механизмов обслуживает
отдельный `Simulation` adapter. Игровой Bevy/BOT adapter использует те же транспорт и каналы, но полный
checkpoint штатной сборки описан отдельно ниже. По сети не передаются `bevy::Entity`.

Адаптер iroh доставляет датаграммы QUIC и привязывает маршрут игрового слота
к удостоверенному EndpointID. IP и iroh используют общий протокол допуска,
проверку ресурсов и пакетный слой Lightyear. SessionId отбрасывает пакеты
прошлой сессии. Прямой UDP предназначен для доверенной сети. В режиме iroh
QUIC шифрует данные и удостоверяет конечные точки.

## Правила сессии

Лобби принимает от двух до четырёх участников. Вход после старта запрещён.
Отпечатки сборки, игровых ресурсов и физики должны совпадать. В отпечаток
игровых ресурсов следует включать CFZ, коллизию и другие значимые для симуляции
данные; косметические замены текстур не должны менять физическую совместимость.

BOT передаётся отдельным надёжным каналом: последовательные блоки до 1024 байт,
общий размер до 4 MiB, проверка BLAKE3, кеш по содержимому. `BotUpload` проверяет
целостность, а не корректность формата BOT: при интеграции обязательно проверять
результат штатным `ra2-formats::bot::decode` до допуска к матчу. Пользовательские
текстуры пока не передаются. Данные оригинальной игры не включены в тесты.

Только HOST может начать игру и менять паузу. Уход HOST завершает сессию.
Пауза не останавливает сетевое время: тики сообщений продолжаются, но физическое
время, позы и ресурсы стоят. Надёжное событие паузы применяется на своём тике,
без ожидания следующего ненадёжного снимка. Старое событие, уже покрытое более
новым подтверждением, не возвращает игру к предыдущей фазе.

## Состояние и предсказание инструментального стенда

Авторитетный шаг — 120 Hz, снимки — 30 Hz, ввод — 60 Hz с повторением последних
12 команд. Команды адресованы конкретным тикам. В пакете нет поля «управлять
чужим роботом»: владельца определяет заранее допущенное соединение.
Буфер ограничивает будущие команды одним игровым секундным окном. Пропавшее
непрерывное управление удерживается максимум 250 ms, затем становится нейтральным;
активации имеют монотонный счётчик и не повторяются от дубликатов.

Снимок содержит позы/скорости всех физических тел, связи, ревизии сборок,
HP/ресурсы/очки и состояние burst-механизмов. Он полный: в первой версии нет
дельта-кодирования или квантования. Большие сообщения фрагментирует Lightyear;
размер внешней датаграммы ограничен 1200 байтами, включая SessionId.

Клиент сравнивает предсказание со снимком **на том же тике**, восстанавливает
подтверждённое состояние и повторяет оставшиеся команды. История ограничена
360 тиками; после более долгого разрыва выполняется явный hard resync.
Prediction не подтверждает повреждения, очки и отрывы. События имеют ID и
надёжную последовательность; HP абсолютны в снимках, поэтому повтор события
не вычитает здоровье ещё раз.

Состояние физического решателя восстанавливается целиком. Нельзя заменить только
narrow phase, оставив старые ссылки islands: четырёхсторонний тест выявил именно
такой assert Rapier. В эталонном adapter создаётся свежий мир с теми же ID и
геометрией, затем восстанавливаются тела, связи и моторы. Это сознательно простой
baseline; стоимость восстановления измеряется отдельно.

Удалённые тела отображаются между снимками по времени HOST. Экстраполяция
ограничена 50 ms. При смене родителя/ревизии сборки интерполяция через разрыв
запрещена. Известные anchors fixed/revolute шарниров сохраняются при сглаживании;
slider требует своего adapter с меняющимися anchors. Renderer получает отдельный
снимок; сглаженные позы не записываются в физику.

## Что именно проверяет стенд

Это инструментальная сцена, **не весь игровой runtime и не оригинальные BOT**.
У каждого робота корпус, рычаг и наконечник; рычаг имеет burst hinge, наконечник
закреплён fixed joint. Используются настоящие тела, контакты и шарниры Rapier,
общий `arena-core::ActuatorState` и общая арифметика силы повреждения.
Контроллер движения упрощён; колёсная модель из `gameplay::drive` не перенесена.
У крепления намеренно низкая прочность для воспроизводимого теста отрыва.

Сценарий включает разгон, встречные контакты, повороты, реверс, серии активаций,
отрыв с сохранением дочернего шарнира, общую паузу и окончательное получение
стабильного checkpoint. Отдельно тестируется запрет prediction-повреждений,
атомарное отклонение неправильного checkpoint и восстановление физики четырёх
роботов многократно подряд. Победа/ловушки оригинальных арен ещё не подключены.

Сеть работает с настоящими сериализованными пакетами Lightyear. Объекты Rust
не передаются клиентам обходным путём. Проверяются RTT 0/25/50/100/150/200 ms,
200 ms в каждую сторону (RTT 400 ms), асимметрия 20/180 ms, jitter ±20 ms,
3% потерь, 1% дубликатов, полоса 64 KiB/s **на направление каждого соединения**,
и blackout отправки 400 ms. Три seed × два размера матча × 11 профилей = 66.
Загрузка BOT дополнительно испытывается на 5% потерь и 2% дубликатов.

Тестовый планировщик использует общий эталон времени, а input lead и задержку
представления задаёт сетевой профиль. Четырёхметочный clock estimator тестируется
отдельно. Автонастройка временных шкал этого инструментального сценария отдельно
не переносилась на игру: native adapter опирается на ACK выполненных команд.
Особенно важно проверить асимметрию: только RTT не определяет задержку в одну
сторону и точное смещение часов.

Текущий `Input` содержит оси и счётчик активаций инструментальной сцены.
Игровой adapter передаёт всю штатную Wiring отдельной схемой `InputCommand` /
`Wiring`, с поколением ввода и состоянием переключателей в checkpoint.
Его текущая версия протокола — 3; handshake, проверка хешей и загрузка BOT
входят в автомат подключения ниже. Разные версии сборки несовместимы.

## Отчёт и критерии

`metrics.csv` содержит агрегаты; соседние CSV — каждую reconciliation с тиками
отправителя/получателя, ошибками, replay и CPU. Трассы сохраняются и для успешных
случаев. У неуспешного запуска ненулевой exit code. Можно повторить любой seed.

- Ошибка prediction: P95 и максимум по всем телам локального робота на совпадающем
  авторитетном тике; отдельные максимумы при смене ревизии сборки и при получении
  ещё неизвестной клиенту паузы. Общий максимум не скрывается. Например, при
  RTT 200 ms + потерях seed 41 дал пик 54,8 cm на первом снимке остановленной
  хостом игры: клиент ещё не получил паузу. Это видимый риск, а не обычная ошибка
  движения; в трассе отмечается `phase_change=true`.
- Ошибка interpolation: сравнение с историей HOST на **времени представления**,
  а не с его текущей, более новой позой. Задержка представления и input lead
  записаны в отчёт: низкая ошибка за счёт большого буфера не выдаётся за низкую
  задержку.
- Доля нехватки снимков, поздние уникальные команды, число replay/hard resync,
  пакеты/потери/пиковая очередь и исходящий трафик HOST. Трафик измеряется на
  границе `DatagramIo`: включает Lightyear и SessionId, исключает IP/UDP/QUIC.
- Полная доставка событий, точное совпадение финальных HP/ресурсов/очков/связей
  и поз **самой предсказываемой симуляции**, а не только полученного пакета.
- CPU всего прогона и reconciliation — измеренное время машины, не сетевое
  виртуальное время; CPU не используется как переносимый CI-порог.

Первичные бюджеты качества: prediction P95 ≤ 5 cm, обычная максимальная коррекция
≤ 50 cm, максимум при смене сборки или неизвестной паузе ≤ 1 m,
P95 угла ≤ 5°, interpolation P95 ≤ 5 cm,
нехватка буфера ≤ 6% (включая отдельный blackout). Точные финальные состояния,
порядок/полнота событий, отсутствие неожиданных hard resync и конечность всех
значений — обязательные инварианты. Пороги не подменяют отчёт о редких пиках.

Эти результаты характеризуют данный fixture и конфигурацию временных шкал.
Они ещё не подтверждают качество полного боя исходных роботов или качество
реального NAT/iroh-соединения. Соединение через настоящий iroh и локальную сеть узлов Mainline проверяют тесты с флагом `real-sockets`.
Для проверки обоих способов входа через публичный relay запустите тест с отключёнными прямыми маршрутами iroh.

```bash
cargo test --locked -p arena-net-io --features real-sockets --lib native::tests::public_room_code_and_endpoint_id -- --ignored --exact
```

## Игровой Multiplayer по IP

Кнопка **MULTIPLAYER** главного меню открывает исходный `multiplayer.gib`.
Exhibition остаётся одиночным режимом. Общая загрузка арены, камера, физика,
ловушки, звук, HUD и результаты находятся в `src/battle`, сетевой интерфейс
и адаптер — в `src/multiplayer`.

1. Хост: Multiplayer → Create Game, настройки/режим/арена → Create Game.
2. Второй игрок: Multiplayer → Refresh и Join Game, либо IP Connect.
   Можно ввести `192.168.1.10`, `192.168.1.10:27666` или для двух окон на одном
   компьютере `127.0.0.1`.
3. В лобби каждый выбирает своего робота кнопкой на карточке и включает Ready.
   Хост нажимает Begin Match после готовности всех участников.
4. После результатов хост возвращает всех в лобби. Выход хоста завершает сессию.

Игровой порт — **UDP 27666**, обнаружение IPv4 LAN — **UDP 27667**.
При обновлении списка игра три секунды слушает ответы LAN. Найденные комнаты появляются над строкой `Searching.`, у которой меняется число точек. По завершении строка исчезает.
Для IP соединения не требуется broadcast. Интернет через прямой IP требует
доступности этого UDP-порта.

### Iroh native networking

В **Create Game** выберите **Iroh native networking**. Восемь цифр и кнопка
**EndpointID** появляются сразу. **Start Game** открывает лобби и запускает
публикацию. Код остаётся виден в лобби. Гость открывает **Join by code** и вводит
цифры с дефисом или без него. Туда же можно вставить полный EndpointID.

Хост и гость вычисляют из цифр и метки протокола один ключ объявления BEP44.
Хост генерирует отдельный ключ iroh и публикует свой EndpointID, прямые адреса,
адрес relay и время публикации. Объявление обновляется при изменении адресов и
каждые четыре минуты. Клиенты принимают его в течение пятнадцати минут. Если
перед записью обнаружена действующая комната с тем же кодом, хост выбирает новый
код и сообщает об этом в лобби. Mainline допускает гонку при одновременной
публикации. Восемь цифр служат для поиска, полный EndpointID позволяет выбрать
конкретного хоста.

Поиск по цифрам работает через UDP напрямую с узлами Mainline. Если сеть
блокирует DHT, кнопка **EndpointID** позволяет воспользоваться штатным адресным
поиском iroh. Для соединения через NAT iroh использует публичные ретрансляторы
и переходит на прямой маршрут, когда он доступен. Хост управляет матчем.
Оба способа подключения используют один игровой протокол.

Общий протокол допуска согласует nonce/назначенный слот/SessionId и manifest; повторяет
запрос при потере ответа, отклоняет несовместимые ресурсы, переполненное лобби
и вход после старта. Отдельный worker обслуживает сеть в реальном времени,
включая загрузку арены, меню и паузу. Перевод в Playing разрешён после Loaded
всех участников. Разрыв соединения во время матча сейчас завершает сессию;
замена отключившегося игрока ботом не реализована.

Настоящий BOT передаётся по хешу с проверкой формата перед созданием сборки.
Все штатные контролы передаются отдельными уровнями и счётчиками фронтов;
сервер сам вычисляет Wiring и силы. Потерянное отпускание клавиши перестаёт
действовать через 250 ms. Хост рассчитывает контакты, HP, ресурсы, отрыв,
очки, ловушки и победу. Клиенты получают позы, состояние механизмов, повреждения,
ревизии сетки, эффекты ловушек и надёжные звуковые события.

**Предсказание штатной сборки подключено.** Собственный робот клиента рассчитывается
сразу на каждом шаге 120 Hz; удалённые роботы сохраняют интерполяцию около 67 ms.
`src/multiplayer/prediction` создаёт отдельный мир Bevy без рендера, со штатными
коллизиями, массами, цилиндрами колёс, шарнирами и теми же системами
`gameplay::drive`, `gameplay::damage::capture`, `gameplay::tyres`. Упрощённый
контроллер инструментального стенда для игрового робота не используется.

Ввод создаётся в 120 Hz, отправляется в 60 Hz. Пакет повторяет до 32 предыдущих
шагов; одинаковые уровни/счётчики передаются сериями, без повторения каждого
удержания клавиши. Хост исполняет одну команду за физический шаг. ACK в снимке —
номер **реально рассчитанной** команды этого игрока. При потерях продолжается
предыдущий уровень, после 250 ms без новых пакетов непрерывное управление
обнуляется. Монотонные счётчики сохраняют короткие нажатия и защищают от повторных
активаций при дубликатах.

Checkpoint содержит позы/скорости, ресурсы, состояния burst-моторов и поршней,
предыдущие значения Wiring, переключатели и подтверждённые счётчики фронтов.
Клиент целиком пересоздаёт состояние решателя Rapier, восстанавливает checkpoint
и повторяет только ещё не подтверждённые команды. Bootstrap коллизий не
продвигает физическое время и не расходует ресурсы. Визуальная поправка к всей
сборке затухает примерно за 80 ms; сглаженные позы не записываются в решатель.

История ограничена 360 шагами. При её исчерпании выполняется ограниченный resync,
без неограниченного replay и уменьшения номера отправляемых команд. Хост может
пропустить номера после разрыва истории до 12 секунд, но всё равно рассчитывает
только один шаг на тик; более далёкий ввод отклоняется. Пауза/возобновление меняют
поколение ввода: пакеты прошлого поколения не могут заново включить мотор.
При отрыве детали у любого робота перестраиваются соответствующие коллизии;
очередь неподтверждённых команд сохраняется.

Prediction не запускает системы повреждений, очков, отрыва, звуков или эффектов.
HP, деформации, победу и разрушение подтверждает только хост. Противники,
обломки и движущиеся платформы в мире prediction — кинематические прокси из
последнего снимка с экстраполяцией максимум 50 ms. Поэтому неожиданное движение
противника или новый удар по игроку может потребовать заметной коррекции;
точный исход взаимного столкновения до получения снимка не гарантируется.

Esc открывает локальное меню без остановки общего матча. Только хост видит
кнопку Pause / Unpause Match. Сам worker продолжает работать во время паузы. F4 включает показатели RTT,
приёма/отправки и сетевого тика, а у клиента также P95/максимум коррекции,
неподтверждённые команды, длину replay и CPU-время шага/сверки.

```bash
# Проверка полного IP handshake, включая потери, повторный вход и несовместимость;
# OS-сокет заменён памятью, Connection::poll и пакетный слой — те же.
cargo test --locked -p arena-net-io --test ip --test session

# Полная штатная физика без окна/GPU/сокетов. Нужны оригинальные игровые ассеты.
RA2_GAME_DIR=/path/to/RobotArena2 cargo test --locked --bin ra2-rs native_prediction -- --ignored --nocapture

# Исходные GIB, настоящий BOT/Rapier, два пакетных endpoint, управление удалённым
# роботом, HP, пауза, локальный prediction и GPU-кадр без открытия окна.
cargo run --locked -- --multiplayer-check --game-dir /path/to/RobotArena2
```

Снимки проверки сохраняются в `logs/multiplayer-*.png`. Настоящий UDP-loopback
по-прежнему выделен в `--features real-sockets`; запрет сокетов в среде проверки
не обходится и не считается успешной проверкой ОС/фаервола/реальной LAN.

### Проверки prediction на оригинальных роботах

Пять проверок с локальными ассетами: матрица C.R.U.S.H. и Walrus (16 случаев),
повторный rollback без повторного расхода воздуха/энергии, пауза/смена поколения,
ограничение истории/resync, отрыв настоящего колеса с сохранением очереди,
неполный checkpoint и движущийся прокси. Матрица: RTT 0/50/100/150/200 ms,
3% потерь, джиттер ±20 ms, 1% дубликатов, 64 KiB/s на направление и blackout 400 ms.
Роботы действительно ездят и активируют burst-механизмы. Контрольные бюджеты:
P95 ≤ 5 cm и максимум ≤ 50 cm; при blackout — 15 cm и 1,5 m. Финальный checkpoint
должен восстанавливать ресурсы и позы точно; предсказание не имеет права менять HP.

`logs/native-prediction.csv` содержит ошибку всех тел на совпадающем ACK, число
повторов, CPU, пропуски команд, трафик, пройденное расстояние и ошибку ресурсов.
Это проверки двух полных штатных сборок на площадке, а не оценка всех возможных
контактов четырёх активно воюющих роботов. Проверка `--multiplayer-check` дополнительно
проверяет, что собственный робот клиента двигается без новых снимков хоста,
пауза очищает очередь, а исходный интерфейс и HUD продолжают рисоваться.
